# Kinematic audit — all 24 commode_c cleaning tasks

Generated by `src/orientation_cost.py` against
`butterfli_ws/.../cleaning_tasks/plans/commode_c/hardware`, using the same
criteria we applied to `toplid` and `hinge_area`. Offline — `rm_algo_*` is a
pure library, no arm involved.

```
python3 orientation_cost.py --plans <butterfli_ws>/.../plans/commode_c/hardware
```

## Scope

* **32 cleaning-point configs** exist for `commode_c`
* **24 have a hardware plan.** Eight do not: `deep_left/right`,
  `front_left/right`, `lid_side_left/right`, `lidsides_back_left/right`
* **4 have ever been executed** through `stage_runner` — `toplid_left/right`,
  `hinge_area_left/right`. The other 20 have never run.
* every task is planned with **`max_velocity_scaling: 1.0`** — the planner is
  permitted to plan right up against the joint speed limits, and it does
* the tool frame **varies per task**: `glove_frame_1` through `_4`. The tool
  offset changes the Jacobian, so orientation cost is not comparable to a
  fixed-tool intuition.

## What this says

### 1. We tuned on one of the safest tasks in the set

`toplid_right` sits at **82 %** — seventh lowest of 24 — and `toplid_left` at
83 %. **Eleven tasks plan at ≥ 90 %, and eight plan at 99.8–99.9 %.** Verified
at full plan resolution, not from the sampled table:

```
lid_seat_hinge_area_left   J1 179.9 / 180 = 99.9 %
side_left                  J1 179.9 / 180 = 99.9 %
seat_ring_bottom_right     J1 179.9 / 180 = 99.9 %
bottomlid_left             J7 224.6 / 225 = 99.8 %
toplid_right               J4 184.2 / 225 = 81.9 %   <- the one we tested
```

CORRECTED 2026-08-12: the `util` column above was first computed at
stride 20 and UNDER-READ the peak by up to 11 points (`hinge_area_left`
88 % sampled against 95 % true, `seat_ring_bottom_left` 89 % against
100 %). A peak is exactly the statistic a stride destroys. It is now taken
at full plan resolution and the count at or above 90 % rose from 9 to
**11**.

Everything we concluded from the `toplid` speed ladder came from a task with
more headroom than most.

### 2. J1 is the joint that binds, not J4

```
binding joint:  J1 x11    J7 x8    J4 x4    J6 x1
```

The "J4 problem" is a `toplid` characteristic. **J1 binds on 11 of 24 tasks and J7 on 8**
— unsurprising, since J1 and J2 have the lower limit (180 °/s against 225 for
J3–J7).

QUALIFIED 2026-08-16 — see `BINDING_JOINT_RESOLUTION.md`. This table is what
**MoveIt's** redundancy resolution does, and the cleaning path never plays the
plan back (`execute_path` is chained `movel`, stage_runner.py:333-400), so the
controller re-solves it. Against hardware the claim splits: **J1 confirmed on
`top_left`** — the highest joint at a commanded 0.25 m/s at every cap, under
every estimator (86 % reported / 90 % house window) — so J1 binding is real,
not a planning artifact. But **`hinge_area_left`
measures J5, not the J1 this table names**, and the plan's overall record is
**11/13, not 13/13**. Read the row as a ranking with a wide-margin caveat, and
note the header claim is too strong: the binding joint is per task, and three
different ones have been measured (H73).

### 4. The saturation is a planning choice, and it is reversible

Every task config sets **`max_velocity_scaling: 1.0`**, so Ruckig is free to
plan up to the joint limits and does. Nothing about the geometry forces
179.9 °/s on J1 — the scaling permits it. Lowering `max_velocity_scaling`
for the saturated tasks buys margin directly, at the cost of stroke time, and
needs no controller change and no vendor answer.

RETRACTED 2026-08-16 (H76). The remedy is inert. `max_velocity_scaling`
appears only in the task-config YAMLs, **no runtime code reads it**, and the
cleaning path is executed as chained `rm_movel` at `cleaning_speed_pct` of the
controller's `line_speed` cap — the plan's time parameterisation is used for
named `movej` poses only. Lowering it changes the saved plan and changes
nothing about how the task runs. The levers that do exist are
`cleaning_speed_pct` / `line_speed`, `line_acc`, the angular cap, blend radius,
and the path geometry. The first two sentences stand as a description of the
plan; only the remedy is withdrawn.

### 5. Orientation cost is universal; its magnitude is not

Median across tasks is **2.5×** — holding the tool orientation costs about
two-thirds of the joint-speed budget on a typical cleaning stroke. But the
peak varies widely: **9.2×** on `bowl_inside_rim_right` and **9.0×** on
`bowl_inside_ring_left` against **1.4×** on `side_right`. The bowl-interior
tasks are the expensive ones, which is consistent with a tool working inside
a concave surface where orientation is tightly constrained.

### 6. Elbow excursion varies 23× per metre

`lid_seat_hinge_area_left` swings the redundant elbow **683 ° per metre** of
tool travel; `toplid` swings **30 °/m**. `bottomlid` swings 831 ° in total —
2.3 full turns. Nothing in the Cartesian limits bounds the rate of that
motion (H46).

## Caveats

* **`util` and `elbow` are computed at FULL plan resolution.** Only the
  Jacobian-derived `ori` columns are sampled at stride 20, because each
  sample costs 14 FK evaluations. `ori` is a ratio whose median is stable
  under sampling; a peak is not, which is why `util` is no longer sampled.
* **Elbow excursion is computed at full resolution**, because unwrapping is
  only valid while consecutive samples differ by < 180°, and at stride 20
  several tasks step 176° between samples. Four tasks still exceed 90 °
  between adjacent waypoints even at full resolution — their elbow figures
  are **uncertain**: `lid_seat_hinge_area_right`, `bottomlid_right`,
  `top_right`, `top_left`.
* Orientation rows of the Jacobian are **Euler rates**, not angular velocity,
  so per-axis attribution is not reported. The held-vs-free ratio compares
  "all orientation constrained" against "none" and is well defined either
  way.
* `util` is what the **plan** demands. Execution via chained `movel` re-solves
  the redundancy itself and ran hotter than the plan on the one task where we
  can compare.

## Recorded findings

  speed limit and 8 at 99.8–99.9 %** (full plan resolution). `toplid`, the only task we speed-tested,

  the planner saturates by permission, not necessity.
* **H49** — **J1 is the binding joint on 11 of 24 tasks**; J4 on only 4. The
  J4 saturation behind H44/H46 is specific to `toplid`.
  *Superseded in scope by H73 (2026-08-16): this counts MoveIt's resolution,

* **H50** — orientation cost median **2.5×** across tasks, range **1.4×–9.2×**;
  the bowl-interior tasks are the expensive end.
* **H51** — **20 of 24 cleaning tasks have never been executed**, and 8 of the
  32 configs have no hardware plan at all.
